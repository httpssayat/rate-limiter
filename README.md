# Rate Limiter

Сервис ограничения частоты запросов для публичного API, который обслуживается несколькими инстансами FastAPI за балансировщиком Nginx.

Состояние счётчиков хранится **только в Redis** — в памяти процессов счётчиков нет, поэтому сервис корректно работает с любым числом инстансов.

**Стек:** Python 3.14.7, FastAPI, Pydantic v2, redis-py (async), pytest, pytest-asyncio, httpx, Docker Compose, Redis, Nginx.

---

## 1. Запуск

Через Docker Compose одной командой:

```bash
cp .env.example .env
docker compose up --build -d
```

Поднимаются:

- `redis` — хранилище счётчиков;
- `app1` и `app2` — два инстанса FastAPI;
- `nginx` — балансировщик на порту `8000`.

Проверка:

```bash
curl http://localhost:8000/healthz
```

Запрос проверки лимита:

```bash
curl -X POST http://localhost:8000/check \
  -H "Content-Type: application/json" \
  -d '{"client_id":"user_123"}'
```

Ответ:

```json
{
  "allowed": true,
  "remaining": 99,
  "reset_at": 1730000000
}
```

Демо-эндпоинт, защищённый middleware:

```bash
curl -i http://localhost:8000/demo -H "X-Client-ID: user_123"
```

При превышении лимита возвращается `429` с заголовками:

```
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
Retry-After
```

### Маршруты

| Эндпоинт | Назначение |
|---|---|
| `GET /healthz` | Liveness-проба для Docker healthcheck |
| `POST /check` | Проверка лимита, всегда отвечает `200` |
| `GET /demo` | Демо-эндпоинт, закрытый middleware |
| `GET /private/data` | Ещё один защищённый эндпоинт |
| `PUT /limits/{client_id}` | Установка персонального лимита |
| `GET /limits/{client_id}` | Чтение персонального лимита |
| `DELETE /limits/{client_id}` | Сброс на общий лимит |

## 2. Тесты

Тесты интеграционные, работают с реальными Redis и двумя запущенными инстансами.

```bash
docker compose --profile test build
docker compose --profile test run --rm tests pytest -q
```

Что проверяется:

- **Приёмочный критерий:** 500 параллельных запросов от одного `client_id` при лимите 100 дают ровно 100 ответов `allowed: true`;
- изолированность клиентов: разные `client_id` не влияют друг на друга;
- общий счётчик: запросы, прошедшие через `app1` и `app2`, учитываются вместе;
- middleware возвращает `429` со всеми заголовками;
- у ключей счётчиков есть TTL;
- после окончания окна лимит восстанавливается (тест использует отдельный инстанс с окном 2 секунды);
- персональные лимиты переопределяют общий;
- снижение лимита посреди окна сразу блокирует клиента.

Дополнительно в `tests/conftest.py` есть сессионный фиксатор, который ждёт готовности всех сервисов перед стартом тестов, чтобы избежать гонок на старте.

## 3. Нагрузка

Нагрузочный тест лежит в `load/exact_500.py` и запускается одной командой:

```bash
docker compose --profile test run --rm tests python load/exact_500.py
```

Скрипт выполняет три шага:

1. **Прогрев** — 50 запросов от временного `client_id`, чтобы прогреть соединения и кэш Lua-скрипта;
2. **Ожидание безопасного места в окне** — если до конца минуты осталось мало времени, скрипт ждёт начала следующего окна, чтобы замер не попал на границу;
3. **Замер** — 500 параллельных запросов от одного `client_id`, считается `allowed` и перцентили `p50`, `p95`, `p99`.

Если `allowed != 100`, скрипт завершается с кодом ошибки `1`.

Пример вывода:

```text
total=500 allowed=100 expected_allowed=100 duration=1.5s
p50=315.8ms p95=544.8ms p99=609.6ms
```

## 5. Принятые решения и их обоснования

### Fixed window вместо sliding window

Выбран фиксированный оконный алгоритм:

```text
window_number = floor(now / window_seconds)
key = rl:{client_id}:{window_number}
```

Причины:

- простая и детерминированная модель;
- легко гарантировать приёмочный критерий: ровно 100 разрешённых запросов из 500;
- одна атомарная операция `INCR` + `EXPIRE` в Redis;
- достаточно для задачи.

Рассматривался **sliding window** через sorted sets (хранение миллисекундных меток запросов и удаление старых записей внутри Lua-скрипта). Он точнее у границ окна, но дороже по памяти и сложнее в отладке. В рамках таймбокса от него отказались.

### Lua-скрипт в Redis для атомарности

Проверка и списание лимита выполняются одним Lua-скриптом:

```text
GET  rl:limit:{client_id}        -- персональный лимит, если есть
TIME                              -- серверное время Redis
INCR rl:{client_id}:{window}      -- увеличить счётчик
EXPIRE (если current == 1)        -- срок жизни ключа
сравнение с лимитом
return {allowed, remaining, reset_at, current, limit}
```

Redis выполняет Lua-скрипт как одну атомарную операцию: между его командами не могут исполняться команды других клиентов. Это исключает гонки между инстансами приложения.

### Время из Redis, а не из приложения

Внутри Lua-скрипта используется `redis.call('TIME')`, а не время локальных часов инстансов. Это гарантирует, что все инстансы считают окно по одним и тем же часам, даже если их системное время расходится.

### Hash tag `{client_id}` в ключах

Все ключи одного клиента имеют одинаковый hash tag:

```text
rl:{user_123}:12345
rl:limit:{user_123}
```

Сейчас используется standalone Redis, но это оставляет возможность перехода на Redis Cluster без изменения логики: все ключи клиента гарантированно попадут в один шард, и Lua-скрипт продолжит работать атомарно.

### `EXPIRE` только на первом запросе окна

Команда `EXPIRE` выполняется только когда `current == 1`. Остальные запросы в окне не обновляют TTL. Это снижает нагрузку на Redis и даёт одинаковый срок жизни ключа — до конца окна плюс небольшой запас.

### Пул соединений создаётся на старте

В `lifespan` создаётся `ConnectionPool` с настройками:

- `socket_timeout=2.0s`;
- `socket_connect_timeout=2.0s`;
- `max_connections=1000`;
- `health_check_interval=30`.

Пул переиспользуется всеми запросами. Без пула каждый запрос открывал бы новое TCP-соединение, что неприемлемо под нагрузкой.

### Fail-open при недоступности Redis

Выбрана политика **fail-open** (по умолчанию `RATE_LIMIT_FAIL_OPEN=true`):

- если Redis недоступен, запросы пропускаются;
- `/check` возвращает `allowed: true`;
- middleware добавляет заголовок `X-RateLimit-Degraded: true`;
- приложение не падает.

Обоснование: rate limiter здесь — вспомогательный механизм защиты, а не основной бизнес-путь. Кратковременная деградация Redis не должна полностью останавливать публичный API. После восстановления Redis сервис продолжает работать без перезапуска.

Компромисс зафиксирован явно: во время недоступности Redis лимиты не применяются. Если требуется строгая политика, переключается переменная окружения:

```env
RATE_LIMIT_FAIL_OPEN=false
```

В строгом режиме `/check` возвращает `allowed: false`, а middleware — `503`.

### Middleware на `BaseHTTPMiddleware`

Middleware перехватывает запросы на защищённые пути (`/demo`, `/private`), вызывает лимитер и либо пропускает запрос дальше, либо возвращает `429` с заголовками:

- `X-RateLimit-Limit` — лимит клиента (персональный, если задан, иначе общий);
- `X-RateLimit-Remaining`;
- `X-RateLimit-Reset`;
- `Retry-After` (в секундах).

`/check` намеренно не защищён middleware — по требованию задания он всегда отвечает `200`.

### Два инстанса и Nginx

Для проверки распределённости используются два инстанса FastAPI и Nginx как балансировщик. В тестах есть сценарий, который шлёт запросы напрямую в `app1` и `app2` и проверяет, что сумма разрешений равна лимиту. Это доказывает, что счётчик действительно общий.

### Персональные лимиты

Персональные лимиты хранятся в Redis:

```text
rl:limit:{client_id}
```

Lua-скрипт читает этот ключ и переопределяет общий лимит. Чтение происходит внутри того же скрипта, поэтому применение персонального лимита остаётся атомарным.

Для продакшена предполагается хранение конфигурации лимитов в PostgreSQL с синхронизацией в Redis как кэш — это даст администрирование и сохранность конфигурации при перезапуске Redis. В рамках таймбокса ограничились Redis.

### PostgreSQL в задаче не используется

По требованию задания состояние лимитов живёт только в Redis. Поэтому миграций и реляционной схемы нет. В `docker-compose.yml` оставлен опциональный сервис `postgres` через профиль, чтобы соответствовать общему стеку задания:

```bash
docker compose --profile postgres up -d
```

### Нагрузочный тест на Python

Нагрузочный тест написан на Python через `httpx` и `asyncio.gather`, чтобы остаться в едином стеке проекта. Рассматривались Locust, k6 и vegeta, но отдельный инструмент для одного сценария избыточен.

Оговорка: генератор работает в том же Docker-окружении, что и тестируемый сервис, поэтому при очень высокой нагрузке может конкурировать за CPU. Для 500 параллельных запросов этим можно пренебречь.

## 6. Методика замеров

Соблюдены условия корректного замера из задания.

### Прогрев

Перед замером `load/exact_500.py` отправляет 50 запросов от временного `client_id`. Это прогревает TCP-соединения с Redis и кэш Lua-скрипта.

### Перцентили вместо среднего

Используются `p50`, `p95`, `p99`, а не среднее. Среднее маскирует редкие, но критичные выбросы.

### Генератор нагрузки не упирается в собственный CPU

Используются поднятые лимиты соединений (`max_connections=500`) и `ulimits: nofile=65536` в `docker-compose.yml`, чтобы генератор сам не стал узким местом.

### Сервис запущен без `--reload`

В `Dockerfile` запускается:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Флаг `--reload` не используется, чтобы файловый вотчер не влиял на замеры.

### Условия окружения

- два инстанса FastAPI за Nginx;
- Redis в том же compose;
- генератор нагрузки в отдельном контейнере, но на том же хосте.

## 8. Важный нюанс(узкое место работы)

Был использован **сетевой стек Docker Desktop на macOS и очередь в asyncio event loop**, а не сам Redis или бизнес-логика.

### Подтверждение

1. Lua-скрипт в Redis выполняет `INCR` + `EXPIRE` + чтение за микросекунды. Это O(1) операции внутри Redis.
2. Нагрузка в 500 параллельных запросов распределяется между двумя инстансами. На каждый инстанс приходится около 250 одновременных запросов.
3. В каждом инстансе работает один uvicorn worker в асинхронном режиме. Все запросы попадают в один event loop и выстраиваются в очередь на I/O к Redis.
4. Docker Desktop на macOS работает через легковесную Linux-виртуалку. Сетевой мост между контейнерами (клиент → Nginx → App → Redis) добавляет существенные накладные расходы по сравнению с нативным Linux.

### Ожидаемое поведение на боевом стенде

На нативном Linux-сервере с несколькими uvicorn worker'ами:

```text
p50 ~ 2-5 ms
p95 ~ 10-20 ms
p99 ~ 30-50 ms
```

Рост `p95` и `p99` в текущем замере связан именно с очередью в одном worker'е и накладными расходами Docker Desktop, а не с ограничениями выбранной архитектуры.

### Что было бы при реальном росте нагрузки

При увеличении RPS до тысяч в секунду первым упёрся бы Redis — не в CPU, а в сетевую связность и количество одновременных Lua-вызовов. В таком случае потребовалось бы:

- горизонтальное масштабирование Redis через Cluster;
- локальный кэш лимитов в памяти инстансов с коротким TTL;
- возможно, переход на batched-проверки.

## 9. Ответы на вопросы из задания

### Вопрос 1

> Что именно делает вашу проверку атомарной? Опишите последовательность операций Redis и объясните, почему между ними нельзя вклиниться.

Проверка выполняется одним Lua-скриптом, зарегистрированным в Redis.

Последовательность операций внутри одного вызова:

```text
1. GET  rl:limit:{client_id}      -- читаем персональный лимит
2. TIME                            -- серверное время Redis
3. INCR rl:{client_id}:{window}    -- инкремент счётчика
4. EXPIRE (если current == 1)      -- срок жизни ключа
5. Сравнение current с лимитом
6. return {allowed, remaining, reset_at, current, limit}
```

Redis выполняет Lua-скрипт атомарно: во время его исполнения другие клиентские команды не исполняются. Это встроенная гарантия Redis.

Поэтому даже если 500 одновременных запросов придут на разные инстансы, Redis выстроит их Lua-скрипты в очередь и выполнит строго последовательно. Ровно первые 100 получат `current <= 100`, остальные — `current > 100`.

Дополнительно использование серверного `TIME` исключает расхождения часов между инстансами.

### Вопрос 2

> Худший случай для fixed window: сколько запросов клиент реально пропустит за произвольные 60 секунд при лимите 100 в минуту?

До **200 запросов** за произвольный 60-секундный интервал.

Сценарий:

```text
окно N:   100 запросов в самом конце, например, на 59-й секунде
окно N+1: 100 запросов в самом начале, на 0-й секунде
```

Формально оба окна легальны — в каждом не больше 100 запросов. Но если взять произвольный 60-секундный интервал вокруг границы, в него попадут все 200 запросов.

Это классическая проблема fixed window. Sliding window устраняет её, но ценой большей сложности и объёма хранимых данных.

### Вопрос 3

> Redis недоступен 30 секунд. Что видит клиент и почему вы выбрали именно такое поведение?

При настройке по умолчанию (`RATE_LIMIT_FAIL_OPEN=true`) клиент видит:

- для `POST /check`: статус `200`, `allowed: true`, `remaining` равен полному лимиту;
- для защищённых эндпоинтов: обычный ответ, в заголовках добавляется `X-RateLimit-Degraded: true`;
- приложение не падает и не требует рестарта после восстановления Redis.

Причина выбора:

Rate limiter в данной задаче — механизм защиты, а не основной бизнес-путь. Кратковременная недоступность Redis не должна полностью ронять публичный API. Компромисс зафиксирован явно: в течение этих 30 секунд лимиты не применяются.

Если требуется строгая политика, включается `RATE_LIMIT_FAIL_OPEN=false`:

- `POST /check` возвращает `allowed: false`;
- middleware на защищённых эндпоинтах возвращает `503 Service Unavailable` с `Retry-After: 1`.

После восстановления Redis сервис продолжает работать без перезапуска — пул соединений автоматически восстанавливается.

## 10. Что не успел


### Хранение лимитов в PostgreSQL

Персональные лимиты сейчас хранятся только в Redis. Для продакшена предполагается:

- таблица `client_rate_limits` в PostgreSQL как источник правды;
- синхронизация в Redis при изменении через API;
- короткий TTL кэша в Redis как защита от рассинхронизации.

Это дало бы администрирование, аудит изменений и сохранность конфигурации при перезапуске Redis.

## 11. Ручная проверка отказа Redis

Для проверки поведения при недоступности Redis предусмотрен скрипт:

```bash
bash scripts/test_redis_outage.sh
```

Скрипт:

1. останавливает Redis через `docker compose stop redis`;
2. отправляет несколько запросов на `/check`;
3. запускает Redis обратно;
4. проверяет, что сервис продолжает работать без перезапуска.

При `RATE_LIMIT_FAIL_OPEN=true` запросы во время простоя Redis возвращают `allowed: true`.
